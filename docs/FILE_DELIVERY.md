# 文件定位、交付与来源输出

Agent 使用两个只读工具：search_knowledge 检索事实，get_document_file 准备原件或登记模板。后者不会发送 QQ 消息，文件字节只在服务端传递。

## 文件定位

明确标题、文档 ID 和登记别名优先。管理员使用 `set-doc-aliases --document-id ID --alias 简称` 设置知识文档别名。标题不匹配或简称未登记时说明无法明确定位；即使历史引用过其他文档，也不能替代当前指定文档。

只有“这份”“刚才那个”“再发一次原文件”等纯指代请求才加载当前用户、当前群或私聊最近八轮中的最近引用。多个候选要求用户选择；明确列出多个完整标题且不是二选一请求时，可以逐个准备文件。

Agent 按语义判断是否要文件，讨论论文或模板不自动发送。服务端另外拦截明确的否定或矛盾措辞，即使模型错误调用文件工具也不会交付。该保护是保守规则，不能保证识别所有自然语言否定；歧义请求应澄清。

发送前核对 active 状态、引用版本、文件名、20 MiB 大小限制和 SHA256。可交付 PDF、DOCX、DOC，不从原件提取检索正文。文件不可用、版本变化或校验失败时停止，不换发其他文件。

## 交付顺序

1. prepare_response 加载历史、运行 Agent、校验来源，返回回答和附件，不保存本轮。
2. QQ 按会话键和原消息 ID 生成请求标识，在 delivery_attempts 保存回答快照。
3. 每个附件和文本页先以短事务领取 sending 状态，结束事务后调用 NapCat。
4. 接口成功记为 confirmed；明确动作失败记为 failed；网络错误记为 unknown。发送途中进程终止留下 sending，同样按结果未知处理。
5. 全部附件和文本页确认后，commit_turn 原子保存完整问答。request_id 唯一索引保证重复提交幂等。

同一事件重试恢复原回答，不再次调用模型；confirmed 项跳过，failed 项可再次领取，unknown/sending 项停止并要求核实。收到新的“再发一次”消息属于新的明确请求，可重新交付。回执不包含文件字节，回答快照保存文件 ID、文件名及校验值；重试时再次检查文件和版本。

多附件部分失败时明确指出已确认项目和当前失败项目；文件成功而文字失败时保留文件确认回执，不保存完整问答。若全部发送成功但聊天保存失败，下次只补提交，不重发已确认内容。confirmed 仅表示 NapCat 接口确认，不能证明用户收到或阅读。没有工作流恢复、调度器或任务队列。

CLI 的纯文本回答在同步返回时提交历史；原件请求会提示通过 QQ 索要，不记录虚假的附件交付。新库共十张必要表；旧库只新增文档别名、聊天请求 ID、唯一索引和交付回执，不删除业务数据、不重建向量。

## 来源输出

模型正文可以提及《文档标题》，但不负责尾部来源列表。服务端移除独立的“参考来源”“来源”等尾段，根据校验通过的工具来源按标题去重，统一附加一次纯文本“参考来源”。模型自写但未实际检索的来源不会保留。
