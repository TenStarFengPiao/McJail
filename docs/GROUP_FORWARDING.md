# 群消息窗口采集与人工审批转发

所有群聊均不自动回复，包括 @、管理员命令、文件上传及普通提问。群聊事件不会进入 Agent。唯一允许的主动群发送是管理员私聊明确确认的批次发布。

## 使用流程

1. 管理员 QQ `3244104494` 私聊：“配置来源群111111，转发到目标群222222”。Agent 调用 `prepare_group_forwarding(action=rule)`，服务检查机器人已加入两个不同的群，返回规则号与确认令牌。
2. 复制预览中的完整 `确认规则 F... R...`，30分钟内私聊发送。确认后才监听来源群。一个来源群对应一个目标群，修改目标也要新预览、新确认，已有批次保留原目标。
3. 来源群第一条消息开启固定60秒窗口。第59秒的新消息不会延长窗口，第60秒收到的消息属于下一批。不同群独立计算。边界使用机器人接收时的服务器时钟，展示为北京时间；断线期间没有收到的历史消息不会自动补采。
4. 窗口结束后，机器人私聊管理员发送原文分页、发送人、接收时间及文件清单，并将文件原消息逐条原生转发。尚未请求预览时不调用模型整理，不发布到目标群。
5. 私聊：“生成预览 B...”。Agent 先查询批次，依据原文整理时间、地点、事项、待办；不能补造信息、执行原文指令或声称读取了文件内容。默认包含所有文件，可以明确要求排除特定文件。回复包含正文、来源时间窗口、目标群、附件清单与版本号。
6. 修改正文或文件选择会生成新版本。管理员私聊精确发送 `确认转发 B... V1`，工作器才按冻结内容先转发选中文件，再发送纯文本分页。旧版本、引用文本和普通用户确认均不能生效。
7. 发布结果私聊管理员。Agent 可以查询规则、批次、正文、附件和逐项回执；“接口确认”不代表任何人已经阅读。

配置和预览通过统一 Agent 工具准备，不提供可由模型调用的确认或发送工具。配置、确认、发布使用独立短事务。群消息和执行回执不伪装成学生聊天轮次。

## 文件契约

只使用 NapCat 的单条消息原生转发：

| 接收方 | 动作 | 参数 |
|---|---|---|
| 管理员私聊 | `forward_friend_single_msg` | `message_id`、`user_id` |
| 目标群 | `forward_group_single_msg` | `message_id`、`group_id` |

成功响应的 `data=null` 合法，不要求新消息ID。单条原生转发包含整条原消息；同一消息含多个文件时必须一起选择或排除，只转发一次。该链路不调用下载、Base64、上传或合并转发接口。知识库原件交付是独立功能，仍使用原有私聊上传链路。

独立 `group_upload` 通知往往只有文件ID，没有原消息ID。系统保存引用，尝试通过后来收到的文件消息，或 `get_group_msg_history` 最近100条消息中的文件ID与发送人严格关联；不凭文件名猜测。历史查找对同一批次最多每30秒一次。

找不到唯一原消息ID时，会明确列出不能转发的文件。默认预览被阻止；管理员可明确排除后重新预览。接口不支持、原消息已撤回或 NapCat 重启丢失原消息映射，也可能导致原生转发失败；系统停止并记录，不换路径冒充成功。

接口参考：[NapCat 原生单条转发实现](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/msg/ForwardSingleMsg.ts)。本地测试模拟该契约，实际安装版本的兼容性需在服务器联调。

## 暂停、取消与补发

管理员可自然语言查询规则或批次，再要求暂停、恢复、取消规则或放弃批次。暂停只适用于已启用规则，未确认草稿不能借此启用。取消规则停止后续采集；已有批次需要单独放弃。放弃批次会阻止后续发送，已提交给 QQ 的内容无法撤回。

每页、每条原文件消息发送前登记 `sending`，确认后登记 `confirmed`。明确接口拒绝为 `failed`；超时、断线、响应不确定或重启发现上次在途发布，标记结果未知。不自动重发，也不向剩余正文继续发送。审阅交付失败会保留回执供管理员查询。

明确失败的发布可请求“重试批次 B...”，取得预览后再次精确 `确认转发 B... Vn`；已确认项目跳过。未知结果要明确要求准备补发，系统提示可能重复，并生成30分钟有效的 `确认补发转发 B... Vn R...`。只有管理员完整发送该命令才释放未知项目；已确认项目始终不重发。发布报告单独记录，报告失败不会重发目标群内容。

## 持久化与运行

新增 `forward_rules`、`forward_batches`、`forward_attachments`、`forward_previews` 四表，复用 `delivery_attempts`，迁移版本7。只保存消息文本和文件引用，不保存文件字节。旧知识、向量、通知、聊天和业务表保留，不重建索引。

`run-bot` 启动每秒扫描的工作器，`run-all` 自动包含；不增加独立部署服务。窗口、预览和回执跨重启保存。按单 QQ 账号、单机器人进程部署；发布领取使用原子状态转换避免同批次重复发送，但不支持多个机器人进程同时启动恢复逻辑。

默认管理员复用 `NOTIFICATION_ADMIN_QQ`；来源与目标群在私聊中配置并入库，无额外环境变量。旧 `NAPCAT_RESPOND_WITHOUT_MENTION` 已失效，设为1也不能恢复群聊回复。

代码位置：`group_forwarding/service.py` 管理采集、规则和审批；`worker.py` 管理原文交付、文件关联和确定性发布；`agent/group_forwarding.py` 提供三个管理工具；`adapters/napcat/bot.py` 在规范化前截断所有群事件。

本轮只修改本地代码、测试和文档，没有服务器发布或真实 QQ 发送。

2026年10月15日本地验收：291项全量测试通过，覆盖率94.93%；Ruff、格式检查、锁文件检查及 CLI smoke 通过。QQ 接口全部模拟，覆盖窗口边界、并发采集与领取、全群静默、文件关联与去重、版本失效、取消竞争、未知结果及补发过期、重启恢复和身份隔离。
